You are a **senior full-stack software engineer and healthtech architect** building a production-oriented teleophthalmology. Your task is to design and implement the dashboard as a polished, clinically realistic, responsive application rather than a generic admin dashboard.

## 1. Product Objective

Build an ophthalmologist-facing workspace that allows a clinician to:

* Quickly understand which patients need attention.
* Triage and prioritize referrals.
* Review patient histories.
* Review retinal/fundus images and investigations.
* Review AI-assisted findings.
* Manage their active patient caseload.
* Collaborate with other ophthalmologists through referrals and second opinions.
* Manage follow-ups.
* Track patients who are overdue or lost to follow-up.
* Maintain privacy through role-based and relationship-based access control.
* Work effectively in a low-bandwidth environment.

The central UX principle is:

> **Show the ophthalmologist the patients who need attention first, then provide everything required to make a safe clinical decision.**

Do not build a generic CRM-style dashboard.

# 16. Access Control Model

This is a healthcare application.

Do not implement access purely through frontend route hiding.

Implement authorization at the backend/API/data layer.

Use:

### Role-Based Access Control

and

### Relationship-Based Access Control

Access should depend on:

```text
User Role
+
Patient Relationship
+
Care Team Membership
+
Purpose of Access
+
Explicit Permission
```

Examples:

An ophthalmologist can see:

* patients assigned to them
* patients they referred
* patients referred to them
* cases where they have been explicitly added to the care team
* second-opinion cases assigned to them

They should **not** automatically see every patient in the platform.

# 17. Temporary Access

Support scoped access.

For example:

```text
Second Opinion Access

Granted to:
Dr. Sarah

Purpose:
Retina consultation

Access:
View images + relevant history + add consultation

Expires:
7 days
```

When access expires, access should automatically be revoked.

# 21. Low-Resource / Uganda Requirements

Design specifically for intermittent connectivity and lower bandwidth.

### Frontend

* Minimize unnecessary API calls.
* Lazy-load images.
* Compress thumbnails.
* Load high-resolution images only when requested.
* Cache appropriate non-sensitive UI data.
* Provide clear loading states.
* Gracefully handle interrupted network requests.

### Clinical workflow

Do not make the entire dashboard dependent on real-time connectivity.

The architecture should leave room for:

* offline queues
* retry mechanisms
* synchronization
* upload resumption

Do not attempt to solve the entire offline system in this dashboard implementation unless the existing codebase already supports it.

# 22. UX Requirements

The dashboard should feel like a modern medical application.

Use:

* clean typography
* restrained visual hierarchy
* compact clinical data presentation
* obvious primary actions
* accessible contrast
* meaningful icons
* responsive layout

Avoid:

* excessive gradients
* gaming-style dashboards
* overly colorful cards
* unnecessary charts
* huge decorative elements
* excessive whitespace that hides clinical information

The design should resemble a serious clinical workspace rather than a startup marketing page.

# 30. Important Product Decision

The application should treat the patient's care relationship as:

```text
Patient
    ↓
Primary Care Team
    ↓
Specialist Collaboration
    ↓
Scoped Temporary Access
```

Not:

```text
Patient
    ↓
Every Ophthalmologist in the Platform
```

This is a core privacy and clinical-governance requirement.
